# codelab-admin：项目维护规范

面向 `nynu-codelab` 组织中 **codelab-admin** team（组织负责人与全栈组长，**Admin** 权限），回答"怎么建仓库、怎么管权限、怎么保证安全、怎么交接"。Maintain 无法管理仓库设置、规则集和安全开关，因此本团队必须持有 Admin。

## 新仓库配置

新仓库创建后，按以下四步完成权限与保护配置。

**总原则**：新仓库 = `software`(Write) + `codelab-admin`(Admin) + CODEOWNERS（codelab-admin 审批线）+ main 分支保护 + 安全开关，五件事齐了才能对外开放协作。

### 前置：创建仓库

见 [仓库命名与权限模型](#仓库命名与权限模型)：由项目负责人或 `codelab-admin` 在组织中创建，归属 `nynu-codelab`，默认选 **Private**。组织不提供项目模板，骨架按规范手工搭。

### 1. 加 team 权限

Settings → Collaborators and teams：

| Team | 权限 | 说明 |
| --- | --- | --- |
| `@nynu-codelab/software` | Write | 全体研发默认推分支、开 PR |
| `@nynu-codelab/codelab-admin` | Admin | 分支保护、规则集、权限与安全开关（Maintain 不足以管理这些设置） |

普通代码仓库**不要**加 `achievement`；只有论文 / 竞赛 / 成果材料类仓库才加它。

### 2. 根目录 CODEOWNERS

**审批线统一为 `codelab-admin`**：任何 PR 改动任何路径，都必须由 `codelab-admin` 团队成员批准，其他团队不能批准合并。

```text
# 默认：所有改动由 codelab-admin（维护团队）批准
* @nynu-codelab/codelab-admin

# 如需让某子目录由专人把关，追加路径行并指向具体 GitHub 用户名
# CODEOWNERS 只认 GitHub login，不写中文名
```

### 3. 分支保护

组织是免费计划，没有组织级规则集，因此这一步每个仓库都必须做，没有"新仓库自动继承"这回事。

Settings → Branches → Add rule，针对 `main`：

- ☑ Require a pull request before merging
- ☑ Require approvals = **1**
- ☑ **Require review from Code Owners（审批人 = CODEOWNERS 中的 codelab-admin）**
- ☑ Require status checks to pass（填上 CI workflow 名）
- ☑ Do not allow bypassing the above settings

`develop` 照抄一份（长期迭代项目）。

### 4. 安全开关

Settings → Code security and analysis，确认全部开启：

- ☑ Secret scanning（密钥扫描）
- ☑ Push protection（推送保护）
- ☑ Dependabot alerts（依赖漏洞告警）
- ☑ Dependabot security updates（安全更新 PR）

新仓库默认可能关闭这些开关，必须手动确认，不要假设它们继承组织设置。

### 5. 不要做的事

- **不直接给个人授仓库权限**——除非要临时隔离某个仓库，否则全走 team。
- **不把 `software` 加成 Admin**——Write 够用，Admin 只给 `codelab-admin`。
- **不在 README 里写"谁负责什么"**——那是 CODEOWNERS 的活，README 只写怎么跑。
- **不把审批线设成 `software`**——合并批准权只属于 `codelab-admin`。
- **不要只依赖规则集或只依赖经典分支保护**——两者并存时要分别核对；组织级规则集管默认分支，仓库级只叠加必需状态检查。
- **不要配一个永远跑不出来的必需状态检查**——检查名必须来自仓库里真实存在的 workflow，否则 PR 永远无法合并。

## 仓库命名与权限模型

CodeLab 组织下的仓库如何创建、命名和管理。

### 命名

- 小写字母、数字、短横线，如 `smart-farm-backend`
- 项目名 + 后缀区分：`xxx-backend`、`xxx-frontend`、`xxx-docs`
- 不用中文、不用大写、不用下划线

### 创建新仓库

组织不维护"复制即用"的项目模板：模板会和真实项目脱节，改一次规范就得同步改一遍模板，也容易让人以为"套了模板就等于合规"。规范靠 CI 检查，不靠复制。

组织已关闭成员自助建仓（Members can create repositories = off），仓库统一由组织所有者创建。

1. 由组织所有者（`codelab-admin` 成员）在组织中创建仓库，归属选 `nynu-codelab`，默认选 **Private**
2. 按下面的命名规则命名，并在 `/main` 前先配好保护规则
3. 搭最小骨架：`README.md`（怎么跑）、`.gitignore`、`.env.example`
4. 在 Actions 页面用组织工作流模板添加标准检查（`.github` 仓库的 `workflow-templates/`），再按技术栈补充 lint / test / build
5. 按 [新仓库配置](#新仓库配置) 完成 team 权限、CODEOWNERS、分支保护与安全开关

> 顺序很重要：先配保护规则和 CI，再有第一个 commit。反过来做，第一个 PR 就会踩到"检查名不存在"或"没人能批准"这类坑。

### 每个仓库必须包含

- `README.md`：项目一句话简介、如何运行、如何贡献
- `.gitignore`：忽略 IDE 配置、`.env`、构建产物
- `.env.example`：环境变量示例（不填真实值）
- `LICENSE`：按项目类型决定（公共项目 MIT，含纯文档仓库；竞赛 / 企业 / 成果项目先不加）
- CI 配置：至少包含组织标准检查（Markdown Lint、PR 标题），再按技术栈补 lint / test / build

每一项都按仓库实际情况核对，缺项在 PR 里说明原因，不要默默省略。

### 可见性

- 公共仓库：面向开源的学习项目、文档
- 私有仓库：竞赛项目、企业合作、未公开成果

拿不准就问项目负责人。

### 团队权限

组织只维护三个 team：

| Team | 仓库权限 | 职责 |
| --- | --- | --- |
| `codelab-admin` | Admin | 组织管理、仓库创建、权限、分支保护、规则集与安全开关（组织负责人 + 全栈组长） |
| `software` | Write | 全体研发，所有代码仓库的默认读写权限 |
| `achievement` | Write（按需） | 成果中心：成果归档、竞赛、论文、专利、软著与企业合作；仅授给成果类仓库 |

项目仓库默认给 `software` Write、`codelab-admin` Admin；工作边界（哪个仓库必须谁批准）写在该仓库的 `CODEOWNERS` 中，不按部门预设子组。完整步骤见 [新仓库配置](#新仓库配置)。

`codelab-admin` 实际需要 **Admin**（组织负责人是仓库管理员）；Maintain 无法管理规则集与安全开关。批量授权用 team、不要给个人开权限，例外情况在 Issue 中说明。

### 规则集与分支保护

组织当前是免费计划，**不支持组织级规则集**（组织级规则集是 GitHub Team 功能），所以每个新仓库都要单独配置规则集和分支保护。这就是 [新仓库配置](#新仓库配置) 必须逐步执行的原因——不要假设新仓库会自动继承保护。

配置完成后，`main` 的行为是：不能删除、不能强推、必须走 PR、至少 1 位 `codelab-admin` 批准、必需状态检查通过。

> 升级到 GitHub Team 后，应把公共规则抽成组织级规则集，仓库级只保留该仓库特有的必需状态检查，避免每个新仓库重复配置。

## 工程安全基线

本节说明代码仓库和 CI/CD 的最低安全要求。安全事件和凭据泄露的处理流程见组织级 [SECURITY.md](https://github.com/nynu-codelab/.github/blob/main/SECURITY.md)。

### 仓库安全

- 不提交密码、Token、API Key、SSH Key、证书私钥和真实 `.env`。
- 只提交 `.env.example`，使用空值或占位符。
- 不把生产数据、企业数据、用户隐私或内部截图提交到公开仓库。
- 依赖升级前检查变更、许可证和安全公告。
- 删除敏感文件不能消除 Git 历史中的泄露，必须轮换凭据并清理历史。

### 代码安全

- 所有外部输入都要校验，不能信任客户端或上游服务。
- 数据库查询使用参数化方式，禁止拼接用户输入。
- 日志不记录密码、Token、完整身份证号、手机号或支付信息。
- 错误响应不暴露堆栈、数据库结构、内部路径或密钥。
- 文件上传、命令执行、反序列化和模板渲染等高风险操作必须做白名单和边界检查。
- 权限检查放在服务端，不能只依赖前端隐藏按钮。

### CI/CD 安全

- 工作流使用最小权限，默认 `contents: read`。
- 第三方 Action 固定到受信任版本，重要仓库优先固定到 Commit SHA。
- 不在 Pull Request 的公开日志中输出密钥。
- 发布密钥使用 GitHub Environment、组织 Secret 或部署平台密钥管理，不写入仓库。
- 发布和回滚操作保留审计记录。
- 生产环境变更需要明确审批和回滚方案。

### 依赖与制品

- 使用锁文件保证依赖可复现。
- 定期检查高危漏洞和废弃依赖。
- 构建产物不提交到仓库，使用 Release、包仓库或镜像仓库。
- 容器镜像使用固定基础镜像版本，避免使用不受控的 `latest` 作为生产制品。

### 事件响应

发现疑似泄露或漏洞时：

1. 停止继续传播，保存必要证据。
2. 立即轮换或吊销可能泄露的凭据。
3. 在 Issue 中说明情况：泄露了什么、什么时候轮换的、需要谁协助清理历史。不需要隐瞒；如果是企业合作项目的凭据，改按合作协议约定的渠道处理。
4. 评估影响范围并制定修复和回滚方案。
5. 修复后记录原因、时间线和改进项。

## 项目与技术资产交接

项目交接属于 GitHub 上的技术协作内容。成员离组、毕业或项目负责人变更时，必须保证代码、文档、环境和运维责任可以继续被接手。

制度层面的离组审批、账号归还和成果归档以飞书 CodeLab 成员手册为准；本节只规定 GitHub 与技术资产的交接方式。

### 交接时机

- 项目负责人或核心维护者离组、毕业或长期无法参与。
- 项目进入维护期、暂停期或移交给新团队。
- 仓库所有权、团队权限、部署环境或密钥负责人发生变化。

### 交接内容

| 类型 | 必须交接的内容 |
| --- | --- |
| 代码 | 仓库地址、默认分支、未合并分支、Issue、PR 和技术债 |
| 文档 | README、技术方案、接口、数据库、部署、测试和复盘文档 |
| 环境 | 服务器、数据库、对象存储、域名、监控和第三方服务 |
| 发布 | 当前版本、发布流程、回滚方案和已知问题 |
| 权限 | GitHub Team、仓库权限、Actions Secret 和部署环境权限 |
| 安全 | 密钥轮换计划、泄露风险和仍需关闭的账号 |

### 交接步骤

1. 创建交接 Issue，列出范围、时间和接收人。
2. 确认 `main` 可构建、测试和部署，记录当前 Commit 或 Tag。
3. 更新 README、部署文档和未完成工作清单。
4. 检查开放 Issue、PR、分支和未解决 Review。
5. 通过飞书或密码库移交账号和凭据，并轮换不再由原负责人持有的密钥。
6. 更新 GitHub Team 和仓库权限，移除不再需要访问的账号。
7. 由接收人执行一次构建、测试或部署验证。
8. 在 Issue 中记录交接结论、遗留风险和后续负责人。

### 交接检查清单

- [ ] 仓库所有权和团队权限已更新
- [ ] 原负责人不再拥有不需要的账号和密钥
- [ ] 所有生产密钥已轮换或确认安全
- [ ] README、部署和接口文档与当前版本一致
- [ ] `main` 构建、测试和部署命令已验证
- [ ] 开放 Issue、PR 和技术债已指派或说明
- [ ] 发布版本、回滚方案和监控入口已交接
- [ ] 交接记录已归档，并建立后续跟踪 Issue

### 禁止事项

- 不要把密码、Token、私钥或真实 `.env` 写入 GitHub Issue、PR 或文档。
- 不要只转交仓库权限而不转交发布、监控和回滚责任。
- 不要在未验证构建和部署的情况下关闭交接 Issue。
